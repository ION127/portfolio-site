BARO는 기획부터 배포 · 운영까지 팀원들과 대화하며 프로젝트 전반에 참여했습니다. 아래는 그중 제가 직접 코드로 올린 작업으로, 2026년 4월 말부터 6월 말까지 여섯 개 저장소에 PR 128개를 머지했습니다.

### 차량 위치가 화면과 배차까지 가는 길

- 차량 위치를 받는 control 서비스를 MQTT → Kafka 한 경로로 정리했습니다. 초기의 Redis · PostGIS 의존을 걷어내고, 관제 화면용 차량 상태를 메모리에 두고 SSE로 밀어 주는 엔드포인트를 만들었습니다.
- MQTT 세션 · 인바운드 클라이언트 문제, ALB 경로(`/control`)의 404를 고치고, 위치 메시지에 운행 상태와 차량 번호를 실었습니다.
- Kafka 컨슈머가 차량 데이터에 운행 상태까지 저장하게 하고, 환경마다 컨슈머를 켜고 끌 수 있게 했습니다.

### 배차와 재배치

- 30초 넘게 위치가 오지 않은 차량은 배차 후보에서 빼고(Redis lastSeen), 차량이 배차 지시에 응답(ACK)하지 않으면 다시 배차하도록 했습니다.
- 운행이 끝난 차량을 수요가 많은 곳으로 자동 재배치하는 흐름을 구현했습니다. 재배치 중인 차량도 호출이 오면 배차로 전환됩니다.
- 게이트웨이에서 어드민 경로를 분리하고, JWT의 role로 관리자 권한을 확인하게 했습니다.

### 관제 대시보드

- 실시간 차량 관제 대시보드를 만들었습니다. 차량 위치, 운행 경로, 재배치 중인 차량(보라색 마커와 목적지)을 지도에 보여 주고, 어드민 로그인과 JWT 인증을 붙였습니다.
- 승객 앱 지도에서 화면 크기가 바뀌거나 사용자가 확대할 때 지도가 깨지던 문제도 고쳤습니다.

### 인프라와 배포 (Terraform)

- baro-dev VPC와 온프레미스를 잇는 Site-to-Site VPN, Kafka를 ECS에서 EBS를 붙인 EC2로 옮기는 작업(Cloud Map DNS), AWS IoT Core 대신 EC2 Mosquitto로 바꾸는 작업을 Terraform으로 했습니다.
- control 서비스의 ECR 빌드 · ECS 배포 파이프라인과, `terraform apply` 뒤 SSM으로 차량 시뮬레이터를 자동 배포하는 단계를 만들었습니다.
- 비용을 줄이려고 내리기 전 RDS 스냅샷 자동 생성과 다음 apply 때 자동 복원, Kafka EC2 t3.small 전환, bastion 제거(SSM 접속), CloudWatch 로그 비용 절감을 넣었습니다. Kafka의 EBS는 실수로 지워지지 않게 막았습니다.

### 차량을 1,500대로 늘리며 고친 것

- 메시지마다 하던 DB 조회를 hot path에서 없애 consumer lag 2.9M을 해소했습니다([운영 기록](#incident-baro-consumer-lag)).
- Kafka가 멈추면 MQTT 수신까지 막히던 producer 대기를 짧게 끊었습니다([운영 기록](#incident-baro-kafka-block)).
- Mosquitto 큐가 넘쳐 메시지가 버려지던 문제를 브로커 큐 설정과 시뮬레이터의 연결 간격(10대마다 0.05초)으로 막았습니다([운영 기록](#incident-baro-mosquitto-queue)).
